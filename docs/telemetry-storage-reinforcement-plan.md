# 遥测存储补强方案：图表精度、跨层查询、流量时间边界与 CSV 资源预算

- 日期：2026-11-11。
- 状态：**验收中**。`bf9b2e7f` 的 26 项 PR CI、两小时 CSV 资格及无 CSV 数据库 E2E 均已通过。复审发现解压统计内存预算漏计，容量及生产规模验证仍有待办。当前结论见文末“长短测通过后的复审”。
- 核查基线：后端 `cfed6d1f67abcd3316983095391728b88ae1652a`，固定 Web 子模块 `4ce5490ca208785b7ef63fa696e3f8e0ae016ad7`。
- 关联：[原设计](telemetry-storage-design.md)、[实施检查点与已有证据](telemetry-storage-implementation.md)。本文件修订与其冲突的图表精度、流量查询和导出资源控制要求，已有验收记录作为原范围证据保留。
- 重点环境：1 vCPU / 1 GiB、SQLite、Docker 后端、真实 HTTPS/Web/Agent；同时保持其他已支持 SQL 驱动的事务与数值一致性。
- CSV 补充约束（2026-11-11）：明确为可运行 1–2h 或更久的后台任务；导出类型不得混淆；进度按真实阶段和工作量报告；所有导出合计占用不超过实例全部有效 CPU 算力的 10%。以下第 6 节及第 8.3 节替代上一版导出预算与验收要求。

## 1. 结论与实施范围

本轮要一起解决四个问题，而不是只提高并发或放宽断言：

1. 图表按实际查看窗口选择约 300 个有效统计桶，支持实时、1h、6h、12h、1d、7d、15d，之后每次增加 15d。
2. 查询按真实覆盖范围组合不同物理层级，避免全局小时精度限制、细层闲置、重复统计和隐藏冷读。
3. 流量走势有匹配 10/20/30 分钟输出的细账本；日计费、周期累计和校准读取独立的业务账本，走势图故障不拖垮计费面板。
4. CSV 采用有 CPU/内存/扫描预算的流式后台处理；限制并发不能冒充限制 CPU。

保留既有不变量：已接收数据持久化、接收及记账幂等、整数 Bytes、现有业务日期/计费周期语义、授权下推、归档与统计完成后才删除 raw、可恢复的跨库 outbox。

## 2. 已核查的问题与证据边界

### 2.1 图表：迁移全局精度与保留层级

- `pkg/metric/telemetry_migrate.go` 的 `legacyResolution` 与所有导入层级取 LCM 后，还会与 1 小时取 LCM；这意味着至少为 1 小时，存在其他非整除层级时还可能更粗。
- `pkg/metric/telemetry_queries.go` 的 `compatibleInterval` 将这个全局值施加到覆盖导入历史的查询。单个粗历史范围不应抬高其他序列、其他范围的精度下限。
- `pkg/metric/telemetry_summary.go` 主要按查询开始时间的年龄选一个来源层级；普通数据使用固定 `b.resolution=?`，没有按各范围现有覆盖生成读取计划。
- `pkg/metric/telemetry_retention.go` 当前为 10s/2h、5m/24h、15m/7d、1h/总留存。即使没有迁移限制，6h 的 5m 层也仅有 72 个桶。
- Web `LoadChart.tsx` 仍请求 700 点，时间窗选择器也没有完整提供 6h、12h、15d、30d、45d 等所需档位。

### 2.2 CSV：限并发、短休眠没有约束持续 CPU

- `web/api/admin/history_export.go` 已有异步任务与单运行 worker，但每批调用 `ExportRawBatch` 后仍会构造数组、映射、格式化与排序。
- 调度器在整批完成后才看宿主机负载；高负载休眠上限 250ms，不是基于任务实际 CPU 时间的预算。
- 相邻时间批可能重复读取、解压同一个大归档。段内的循环让步不等于完整导出链路已经限速。
- 导出完成后仍调用 `compactHistoryExportCSV`，重新读取并改写整份 CSV；这个阶段也必须纳入预算或取消。
- 当前 CSV 按 30s 槽保留确定的一条样本，同槽额外观测被忽略。它是兼容采样格式，不是无损原始明细。
- `setHistoryExportProgress(job.ID, 1+int(next.Sub(job.Start)*98/total))` 按扫过的时间跨度映射到 1–99%，没有表示数据密度、压缩率、重复解压、整理排序和收尾成本。前 80% 时间范围很稀疏、后 20% 很密集时，进度快跑到 80% 后很久不动完全可能；这不是“已完成 80% 工作”的可靠证据。
- Web 当前直接展示单个 `progress`，没有清楚区分等待配额、运行、暂停、重试与收尾。现有代码虽已有后台任务说明，但仍不足以表达小时级冷导出、真实阶段和剩余工作的区别。
- 当前启动加载只恢复 `done` 任务，并删除 `.part/.tmp`。已有前端 localStorage 记住任务 ID，不等于运行任务已经持久化、服务重启可恢复。

### 2.3 流量：用户报告的调用链成立

已在固定源码中确认：

```text
TrafficTrendPanel
  -> BrowserService.GetTrafficTrend
  -> dashboard.LoadTrafficTrend
  -> MetricUsageByIntervalBatch
  -> telemetryUsage / TelemetryUsageBatch

BillingTrendPanel
  -> DashboardService.GetDashboardCharts
  -> loadDashboardTraffic
     -> 已结算日账本 + 校准调整
     -> MetricUsageByHourBatch（今天）
     -> LoadTrafficTrend（24h/20m）
  -> 任一上述调用失败，当前实现会使整个 traffic 模块失败
```

`loadDashboardTraffic` 在趋势失败时直接返回错误；模块缓存随后用仅含 `Error` 的结果替换整个 traffic 模块。Web `BillingTrendPanel` 判断 `error || charts?.traffic.error`，因此已成功读取的日账本也无法展示。独立走势请求失败时，`TrafficTrendPanel` 同样显示“数据暂不可用”。

另需注意：今天的流量也使用小时切片查询，因此不能只把最后一次 `LoadTrafficTrend` 改为忽略错误；今天读数本身也需要适配新账本。

### 2.4 首边界：小时切片不能回答被截断的 20m 窗口

`database/trafficledger/telemetry.go` 中 `ApplyTelemetry` 将增量写入按小时分组的切片，并在计费周期边界处分割；`FirstObserved/LastObserved` 只保留观测范围，不能还原小时内的流量分布。

`web/dashboard/traffic.go` 中：

```go
displayEnd := now.In(BeijingLocation).Truncate(interval).Add(interval)
start := displayEnd.Add(-bucketCount * interval)
// 实际读取终点是 now，不是 displayEnd。
MetricUsageByIntervalBatch(ctx, clients, start.UTC(), now.UTC(), interval)
```

当 `interval=20m` 时，连续有数据的典型例子为：

| 当前时间 | 显示末边界 | 24h 查询开始 | 与第一个小时切片的关系 |
| --- | --- | --- | --- |
| 10:05 | 10:20 | 前一天 10:20 | 切开 10:00–11:00 |
| 10:25 | 10:40 | 前一天 10:40 | 切开 10:00–11:00 |
| 10:45 | 11:00 | 前一天 11:00 | 首边界可与整小时对齐 |

`TelemetryUsageBatch` 的断言：

```go
if s.FirstObserved < start.UnixNano() || s.LastObserved > end.UnixNano() {
    return nil, nil, fmt.Errorf("%w: partial traffic ledger slice", metric.ErrTelemetryCoverage)
}
```

如果重叠切片确实包含窗口外观测，就会命中该错误。用户说的“每小时有 40 分钟容易触发”在密集、连续历史下成立；稀疏节点是否触发还取决于实际 `FirstObserved`，不能把它说成所有节点所有请求都必然失败。

这条断言原本是在阻止不精确计费，不应直接删除。真正的错误是：用只能回答完整小时的存储表示，承接了更细的在线查询契约。

### 2.5 更隐蔽的问题：不报错也可能错误分桶

现代码将整个切片的 `UpBytes/DownBytes` 加到 `s.Start.Truncate(interval)` 对应的桶。

例如完整查询 10:00–11:00，输出间隔 20m，真实上报增量分别为：

| 观测归属时间 | 上传增量 |
| --- | --- |
| 10:05 | 100 Bytes |
| 10:25 | 200 Bytes |
| 10:45 | 300 Bytes |

小时切片只剩 600 Bytes。当前逻辑会全部放进 10:00 桶，无法得到应有的 100/200/300。

因此，修到“请求返回 200”仍不合格。必须同时核对每桶字节数、总和及时间归属。不得将 600 平分成 200/200/200 并称为真实计量。

### 2.6 末边界：存在并发快照不一致风险，尚非现场证实

调用方先捕获 `now`，`telemetryUsage` 随后运行 `ensureTelemetryFresh`，读取期间后台也可能消费新事件。如果新提交的观测晚于先前捕获的 `now`，同一个可变小时切片就可能出现 `LastObserved > end`。

这不需要 Agent 时钟错误也可能发生；Agent 未来时间则是另一个需要质量检查的输入问题。当前读取也没有把所有节点状态与切片固定在同一个业务读取快照。

代码支持上述竞态的可能性，但本次没有生产库或该次请求的完整并发跟踪，不能把它写成已在现场复现。将其纳入可控屏障回归测试。

### 2.7 额外资源风险：前台读取仍推动记账

`ensureTelemetryFresh` 在前台尝试投递 128 个 outbox 事件，正好投递满 128 时返回 catching-up 错误。即使有界，它仍让看板读取参与数据库写入、争用元数据库写者，并把积压传播为读失败。

补强后由后台持续推进记账；前台只读已提交水位并返回数据截至时间、积压/过期状态。正常缺口、暂未追平不能伪装成零流量，也不能默认升级为整个面板的 500。

## 3. 图表目标与物理保留策略

### 3.1 输出窗口

目标是有足够真实采样的每条曲线约 300 点，常用档位允许 300–360 个桶；不靠插值或补零凑数。

| 窗口 | 建议输出间隔 | 完整窗口桶数 |
| --- | --- | --- |
| 实时 | 按实际上报，滚动保留最近约 300 点 | 约 300 |
| 1h | 10s | 360 |
| 6h | 1m | 360 |
| 12h | 2m | 360 |
| 1d | 4m | 360 |
| 7d | 30m | 336 |
| 15d | 1h | 360 |
| 30d | 2h | 360 |
| 45d | 3h | 360 |
| 60d | 4h | 360 |
| 75d | 6h | 300 |
| 90d | 7h | 约 309 |

之后每次增加 15d，按目标点数与实际可用来源粒度推导输出间隔，不以 30d 封顶。非整 15d 留存提供“全部留存”。窗口不超过对应指标真实留存；多指标留存不同时，逐序列报告缺失。

上述目标面向截至当前的最近窗口。几个月前的一小时如果只剩小时统计，不能承诺仍有 300 点。

### 3.2 建议物理层

| 层级 | 建议保留 | 用途 |
| --- | --- | --- |
| 10s | 3h | 1h 图与近期放大 |
| 1m | 48h | 6h/12h/1d 图 |
| 15m | 14d | 7d 图与近期历史放大 |
| 1h | 指标总留存 | 15d 及以上图 |

保留期限受指标总留存裁剪。已有 5m、30m 等层级继续作为有效来源，不因默认层级改变而丢弃其查询能力。最终默认值还需通过活跃序列数量、标签基数、每序列实际存储量及写放大基准，不把少节点的结果外推到所有规模。

### 3.3 汇总推进

- 小桶闭合后按输入水位与版本逐级晋升，避免每个上报批次对所有层级重复执行 JSON 读改写。
- 增量推进、迟到修正、重试和幂等状态一并提交；数据质量策略区分观测时间与接收时间。
- 粗层完整覆盖对应输入水位后，才允许回收细层；单有一个同名粗桶不代表已经包含全部迟到增量。
- 不做每 30s 全库重汇总；保留已有按完成进展调度和有界事务原则。

## 4. 跨层查询计划

1. 由窗口和目标点数确定输出网格，再查实际存在的来源覆盖，不再只按 start 的年龄选一个固定层。
2. 优先使用能完整构成输出桶的较粗来源；缺少粗桶时向细桶回退。
3. 例如两个 15m 桶或六个 5m 桶可以构成一个 30m 桶；一个 1h 桶不能被拆成两个真实 30m 桶。
4. 读取计划在同一序列、输入身份及时间范围内不重叠。同一采样在多层出现只计一次；不同分段中各自真实的数据仍需正确合并。
5. 不能只改为 `resolution<=?` 然后把所有结果相加；必须识别多层表示关系和已提交覆盖水位。
6. 使用半开区间与固定读取水位衔接热尾、汇总和边界数据；没有细来源时明确标注边界精度，不靠完整粗桶替代部分窗口。
7. 普通图表不隐式解压冷归档；扫描、序列数、内存、执行时间和返回点数分别有预算。

统计合并：平均值合并 sum/count；丢包率合并失败/总探测次数；方差合并可组合状态；P95/P99 使用可合并分布摘要并标注近似口径；first/last 使用时间及稳定次序。不得平均各桶平均值、百分位或丢包百分比。

响应应区分 `requested_interval`、实际输出间隔、分段来源精度、覆盖范围、空缺原因、统计水位和边界是否近似。必要的协议变更使用向后兼容字段，并同步固定协议/Web 版本。

## 5. 流量账本的时间契约与查询拆分

### 5.1 不可接受的修法

- 不能删除 partial-slice 断言后，把整个小时计入截断窗口。
- 不能简单跳过首尾重叠切片，造成少计。
- 不能把 1h 流量均分到三个 20m 桶，冒充真实走势。
- 不能把请求改为整小时就认为前端 20m 契约已经满足。
- 不能为规避末端竞态把 end 扩大到未来整小时，读入请求范围以后的流量。
- 不能在正常看板/计费请求中回扫大范围 raw 或解压归档修账。

### 5.2 按用途分开的数据各自负责

| 数据 | 建议表示与留存 | 读取职责 |
| --- | --- | --- |
| 近期流量走势 | 每节点 1m 整数增量桶，初始保留 48h | 精确组成 10m/20m/30m 的完整桶 |
| 当前可变尾部 | 短期持久事件增量，初始保留最近 5m，并覆盖所有尚未安全封口的分钟 | 计算最后未闭合分钟、固定终点和并发快照边界 |
| 既有小时账本 | 保留其业务用途及既有 35d 策略，验证后再调整 | 完整小时钻取与兼容粗历史 |
| 日期/周期/累计/校准 | 独立整数账本，按业务期限保留 | 日计费、周期统计、校准、告警 |

走势分钟桶独立于指标图表的统计层，值为已确认流量增量的整数和，不从网络速率平均值反推字节。无须为每个 CPU/内存样本生成额外业务明细。

增量的时间归属沿用现有被接受事件的业务口径。本轮不把跨上报间隔的增量擅自均摊到每秒，也不顺带更改日期时区或计费重置口径。所谓精确，是相对于该已定义的事件记账口径，不声称恢复未观测的逐包发送时刻。

### 5.3 写入与一致性

在元数据库的同一个幂等事务中更新消费水位、累计/日期/周期账本、走势分钟桶及短期尾部；失败整体回滚。重放事件不能重复累计任何一层。

读取使用一致的元数据库快照，获得已提交记账水位、实际读取截至时间和覆盖状态。实时接口在建立快照时确定 as-of，不混用请求开始前捕获的旧 now 与后来更新的可变聚合行；固定历史 end 则严格遵守该终点。

最后一个未闭合分钟从有界尾部读取，已闭合分钟从分钟账本读取，按同一水位去重衔接。尾部淘汰须等待对应分钟安全封口及查询租约结束；长停机或迟到不能使“最近 5m”成为无条件删除未交接事件的理由。

不可信未来观测不能通过扩大查询 end 被静默纳入。保留原时间及质量诊断，沿用/明确输入时间校验策略，不在本轮无说明地更改已有计费时间归属。

首边界采用对齐的分钟来源；任意历史范围若切在已回收细节的桶内部，必须返回该范围精度不足的结构化状态，不伪造精确结果。

### 5.4 查询接口分工

- `TrafficTrend`：读取分钟走势与短期尾部；正常返回 24h/20m 的 72 个桶，并报告尾桶是否完整、覆盖与 as-of。
- `BillingDaily`：直接读取已提交日期账本及校准调整；今天也读取增量维护的当天账本，按同一快照提供截至水位。
- `BillingCycle` / 校准：读取周期账本、首日边界状态和调整；不依赖走势图是否可用。
- 完整小时钻取保留明确的小时契约；任意边界的精确查询不再由只有小时总量的通用函数假装满足。

将前台 `ensureTelemetryFresh` 的记账推进移交后台持续任务。前台报告 `accounting_through`、数据截至时间和追赶状态；必要时在短预算内等待水位，但不接管积压消费。

现有 `TelemetryUsageBatch` 的 256 节点上限也需由调用方正确分批或由新批量 SQL 路径承接；分批必须共享读取快照和扫描预算，不能为全局看板无界开 goroutine。已核查这个限制存在，尚未证明它是本次现场原因。

### 5.5 错误隔离与前端展示

- 日计费、24h 走势、排名及今天累计分别携带状态，不再用一个 `traffic.error` 覆盖全部子结果。
- 走势失败、缺少细历史或回填中，不得隐藏已可用的日账单；当天数据不可用时保留已结算日期，并标记当天未知。
- 历史不足、记账追赶、降级精度、真实无流量、数据库失败分别表示。未知值不是 0 Bytes。
- 有上次成功结果时可以继续展示，但必须标记 stale/as-of；保留原授权范围，不能把其他账户的缓存拿来降级。
- 错误映射区分请求非法、暂时不可用、数据覆盖不足和内部故障；预期覆盖不足不再一概返回 CodeInternal。
- 缓存键包含授权/节点集合、窗口、实际网格、存储代次/覆盖版本及必要水位。取消一个请求不取消共享读取，缓存也不能跨过已清空/切换的数据代次。

## 6. CSV 的读取与资源重设计

### 6.1 任务定位与前端承诺

CSV 在 raw 进入冷归档、在线主要使用 rollup 以后，是需要解压和转换历史数据的后台工作。完成时间可以是 1–2h，数据更大或前台繁忙时还会更久；优先满足资源上限和结果正确性，不以抢占前台 CPU 换取短时速度。

所有模式都采用“创建任务 -> 服务端后台生成 -> 完成后下载”。即使图表 CSV 通常很小，也复用任务模型与预算，避免特例绕过限额。

前端必须做到：

- 页面标题/按钮明确为“后台导出任务”“创建后台任务”，不让用户误以为点击后立即下载。
- 原始明细旁持续显示：“历史明细需要读取并解压冷归档，可能耗时 1–2 小时或更久；关闭页面不影响任务，完成后可在任务列表下载。”这只是说明可能时长，不是两小时完成保证。
- 提交后快速返回任务 ID 和初始状态；请求处理不在前台做完整扫描、解压或行数预统计。
- 创建时展示所选模式、节点/指标、时间范围、粒度/聚合口径、可用覆盖和 CPU 上限。初始大小/时长只能显示为估算或“正在评估”，不能伪装成已知值。
- 任务列表独立于当前表单，支持刷新、关闭页面后返回、查看详情、取消、必要的手动暂停/继续，以及完成文件下载。
- 任务属于有权限的账户/授权范围。localStorage 只作为快速定位，服务端持久任务记录才是权威；切换账户不得展示另一账户的缓存任务。
- 完成后的下载请求只传输既有文件；“生成进度”和浏览器“下载进度”分开。

### 6.2 三种导出类型必须明确区分

| 用户可见类型 | 数据来源 | 一行的含义 | 精度与缺口 | 成本预期 |
| --- | --- | --- | --- | --- |
| 图表汇总 CSV | 既有汇总 + 有界热尾，使用同一查询计划 | 一条序列在一个明确时间桶内的统计结果 | 标出输出间隔、聚合算法、样本数与实际覆盖；不是 raw | 相对较小，但仍受后台预算 |
| 原始观测 CSV | 实际保留的热明细 + 冷归档 | 一条实际观测；稳定长表 | 保留原始时间、身份、标签和值；不做 30s 抽样 | 可能很大、很慢，允许小时级 |
| 30 秒采样 CSV（兼容格式） | 实际原始观测，沿用旧槽位选样规则 | 每序列每个 30s 槽的确定性样本/兼容宽表 | 明确抽样规则；同槽其余样本不输出 | 文件较小，但仍可能需要完整读冷归档 |

补充规则：

- 30s 采样导出不是“30s 平均值”，也不保证计算比原始明细便宜；改变输出采样不会自动免除解压输入的成本。
- 图表汇总 CSV 的 `avg/min/max/p95/...` 与实际粒度是任务参数，不与采样槽宽混为一谈；不同时区或留存的指标要保留各自覆盖元数据。
- 原始 CSV 使用明确的 `observed_at`、`received_at`（如果来源有）、`entity_id`、`metric`、`tags`、`value`、`unit`、稳定观测身份等列；来源原本没有的字段不得编造。
- 图表 CSV 使用 `bucket_start/bucket_end`、`value`、`aggregation`、`sample_count`、来源精度和覆盖字段；不能通过补零或插值凑出原始记录。
- UI、任务清单、文件名及导出元数据都包含 `mode`。资源/网络/Ping 是 `category`，不能再借 `type` 同时表达数据类别与导出精度。
- 原始数据已过期或仅剩汇总时，创建/规划阶段明确指出不可导出的范围。用户主动改选汇总模式才创建新的任务，不得在原始任务中静默降级。
- 不为缺失历史偷偷生成部分“成功文件”；如需允许部分覆盖，必须是明确任务参数，结果元数据列出缺失范围。
- 旧 API/文件格式保持版本化兼容；新前端明确提供三种模式及说明，默认不把已有 raw 请求改成汇总。

### 6.3 持久状态机与生命周期

任务状态与执行阶段分开存储，避免“running 80%”同时代表所有情况。

| 状态 | 含义与 UI |
| --- | --- |
| queued | 已创建，显示排队位置/等待时长，不显示假百分比 |
| running | 正在指定阶段工作，显示该阶段计数与吞吐 |
| paused | 因用户、CPU 配额配置、前台压力或磁盘/内存压力暂停，显示原因与已暂停时长 |
| retry_wait | 可恢复故障等待重试，显示原因和下次尝试时间；不能仍装作正在推进 |
| recovering | 服务重启后验证检查点、恢复租约和输出位置 |
| cancel_requested | 取消已接收，等待安全停机与清理；不能在文件仍写入时宣称取消完成 |
| cancelled / failed | 终态，显示原因和已完成阶段，不提供不完整文件下载 |
| ready | 数据、文件校验和目录发布全部成功，才可下载且显示完成 |
| expired | 完成文件已过期或被删除，不再展示可下载按钮 |

状态、参数、模式、固定数据水位、manifest、检查点、版本与进度计数持久化。服务重启不能再一概删除进行中的 `.part`；先核对任务身份/版本、有效输出偏移和来源租约，再恢复或给出可解释失败。

文件保留 48h 从 `ready_at` 开始计算，不从提交时间扣掉排队/运行/暂停时间。运行任务的保护租约、最长等待/运行安全策略独立配置，不能用“已生成文件 TTL”误杀跑了一两小时的任务。租约要能识别失联 worker 并回收，不能永久阻止必要留存清理。

### 6.4 先冻结清单，避免以时间跨度冒充工作量

在有预算的规划阶段固定授权、范围、读取水位和来源清单，记录：

- 热数据读取边界及可恢复的主键/游标；原始归档文件、帧、长度、校验和和覆盖。
- 去重后的待扫描压缩字节/帧数；同一文件多时间段命中仍只算一次读取工作。
- 能可靠获得的记录数、未压缩字节数、序列数；不能靠额外全量扫描去“算准”进度分母。
- 来源缺失、仅剩汇总、预计输出空间与临时空间；无法可靠估算则如实标注未知并设置实际空间保护。
- 格式/统计版本、排序方式和任务去重键。任务参数被冻结，运行过程中表单变化不改变正在生成的文件。

创建请求只完成有界校验和轻量保留预约，完整 manifest 构建属于后台预算内工作。排队/规划期间的范围保护也必须有授权、容量与期限约束，防止大量任务长期钉住全部历史。

### 6.5 进度：按实际阶段报告，不再制造一个假的总百分比

**主界面用阶段条与阶段内进度，默认不提供无法可信估计的“整个任务已完成 X%”。** 不把时间范围扫描进度改个权重映射成 0–80%，也不提前占一个固定 20% 给收尾。

| 阶段 | 阶段进度依据 | 总量不确定时 |
| --- | --- | --- |
| 规划与检查 | 已处理目录页/已确定文件与帧 | 不定进度，显示已发现量 |
| 读取、解码与生成 | 已完成处理并确认的唯一输入单元/字节；同步显示 decoded_records、written_rows、output_bytes | 展示真实计数和吞吐，不显示百分比 |
| 合并/排序（仅需要时） | 已合并段/已消费输入字节；每一遍单独显示 pass 与分母 | 显示阶段及处理量，不能沿用上一阶段百分比 |
| 校验与发布 | 流式校验已随写入完成；剩余 flush/fsync/原子发布使用明确子状态 | “正在落盘/发布”，不假装已完成或一直显示 99% |
| 完成 | 校验、持久化与发布全部成功 | 唯一可显示任务 100% 的状态 |

进度计数要求：

- 分子只计完成转换/写入确认的工作单元。打开文件、读取器预读到 EOF、将数据放进内存队列，均不等于该文件已经处理完。
- 新格式以独立帧/有界块为进度和检查点单位。一个旧 zstd 流没有可靠细分总量时，报告文件级已完成数、当前文件的解码条数与输出量；不拿底层文件 seek 偏移冒充解码完成百分比。
- 区分 `source_scanned_bytes` 与 `source_completed_bytes`。前者用于诊断读放大，后者才可作为阶段进度依据；重读同一输入不重复增加完成量。
- 同一阶段的固定分母进度单调，暂停期间冻结。阶段变化要显示新的阶段名和其自身进度；恢复阶段显示“从检查点恢复”，不让旧缓存的 80% 看起来仍在工作。
- 恢复校验单独报告“已校验的已提交输出字节 / 固定前缀总字节”。每次恢复从字节 0 重新验证；持久观测进度不作为跳过校验的凭据，不推进生成行数或已确认检查点。
- 热/冷数据、稀疏/密集区间成本不同，不能按“过去 24 天/总 30 天”推导工作百分比。
- 正常直出路径只有一遍读取/转换；逐行统计校验和，不另起一次完整文件扫描来做进度或校验。格式确实需要额外合并遍数时，在任务规划和 UI 中明确说明。

允许的 UI 示例：

```text
后台任务 · 原始观测 CSV · 正在解压并生成文件
本阶段已完成 1.8 / 4.2 GiB 输入（43%）
已生成 3,240,000 行 · 输出 610 MiB · 最近 5 秒有进展
CPU 上限：全部有效 CPU 的 10% · 预计还需约 45–90 分钟
可以关闭页面，任务继续运行
```

其中数字仅为界面示例，不是当前实测。若输入量或 ETA 不可靠，则分别显示已处理量/“剩余时间暂无法估计”。

### 6.6 ETA、心跳与“卡住”的可观测性

- ETA 使用已完成工作单元的实际耗时、CPU 限额和近期吞吐，按来源类型及阶段估计；至少积累稳定样本后才显示区间，不作秒级倒计时承诺。
- 没有可靠的后续阶段成本时，只显示“本阶段预计剩余时间”，不能把它叫任务剩余时间。
- 因限额节流、资源压力、用户操作或重试而等待时，显示对应原因；暂停期间隐藏或冻结 ETA，并显示等待时长。
- 服务端分别提供 `last_heartbeat_at`、`last_progress_at`、`wait_reason`、当前文件/帧（对用户隐藏服务器绝对路径）、处理行数和实际吞吐。
- 心跳存活但无工作推进时，展示“受 CPU 配额限制”“等待磁盘写入”“等待资源恢复”等真实状态；无解释的长期无进展才进入停滞诊断，不能每隔几秒自动重启整个导出。
- 状态轮询本身有界：前台可见时约 5s，一次批量取列表；后台页面约 30s，支持 ETag/退避。网络短暂失败后自动恢复轮询，不用每秒 toast，也不把客户端断开当任务失败。
- 统计/心跳可每数秒合并持久化，不能每导出一行就写任务数据库。规划、状态维护和恢复本身同样纳入导出控制服务的资源预算。
- `recovering` 同样展示当前 worker 心跳及资源组实测值；不沿用生成阶段吞吐或 ETA。I/O 等待时长必须包含尚未结束的当前等待，不能到等待结束才突然增加。

### 6.7 CPU 上限：所有导出合计不超过全部有效算力的 10%

这里将用户所说的 CPU steal 落实为“导出任务占用的 CPU 时间占全部有效 CPU 容量的比例”。操作系统的 hypervisor steal 指标还受宿主机调度影响，不能当作应用配额计数器。

定义：

```text
C_eff = 当前实例实际可用 CPU 算力
        （裸机/VM 的 CPU 亲和性、可用逻辑 CPU，或容器 cpuset 与各级 quota 的共同上限）
导出总 CPU 上限 = 0.10 × C_eff 核
导出占比 = 全部导出 worker/子进程消耗的 CPU 秒 /（经过秒数 × C_eff）
```

| C_eff | 所有导出合计最多使用 |
| --- | --- |
| 0.5 核 | 0.05 核 |
| 1 核 | 0.10 核 |
| 2 核 | 0.20 核 |
| 4 核 | 0.40 核 |
| 8 核 | 0.80 核 |

这不是“每个任务 10%”，也不是“一个核的 10%”，更不是“当前空闲 CPU 的 10%”。例如宿主机 8 核但容器只分到 1 核，按 1 核有效容量设置 0.10 核上限，避免容器内部被吃满。C_eff 来自主 Komari 实例/部署获分配的总容量，不能再把导出子组自身的 9%/10% 配额当分母而递归缩减；独立 worker 服务从同一控制端获得该容量与总预算。

严格约束：

- 三种 CSV 模式、全部任务、worker 子进程、解码器线程、GC、排序、校验、规划与恢复共用一个导出资源组。默认运行并发 1，未来提高并发也不增加资源组总上限。
- 上限配置只允许进一步降低，当前产品要求下不得由“自动加速”或 UI 调高到 10% 以上。空闲机器也不借用额外 CPU；跑一两小时可以接受。
- 默认实际执行配额建议留安全余量，例如先按 9% 配置并验收，10% 是总验收上限；不能因统计取整、调度控制或辅助进程变成 11% 仍声称达标。
- 进程 nice/CPU weight、单线程、GOMAXPROCS、`Gosched` 或事后 sleep 都不能单独作为硬限额证明。
- Linux 主路径将独立导出服务及所有子进程放入同一受控 cgroup，配置 `cpu.max`，关闭额外 burst，所有阶段使用普通受配额调度的任务。Docker 可由同镜像的独立 export-worker 服务获得明确 CPU 配额，不要求主服务容器取得特权。
- CPU 周期配额可用 `quota = period × 0.10 × C_eff` 表达；例如 1 核、100ms 周期，上限是 10ms CPU 时间/周期，实际可按 9ms 留余量。小配额低于平台最小粒度时可延长周期并进一步降低实际 quota，确保 1s/10s 窗口边界预算仍成立；无法满足则报告不可运行，不能向上取整或放宽验收突破上限。
- 周期配额约束累计 CPU 时间，短调度片仍可能瞬时运行满核。验收采用明确周期与 1s/10s/全程 CPU 时间窗口并保留调度边界记录，不承诺每个毫秒都只有 10% 活跃；不能只拿两小时平均值掩盖前一分钟打满。
- 运行中实例 CPU 配额/亲和性降低时重新计算上限，调整期间停止发新工作；不能继续沿用宿主机核数或旧配额。
- CPU 时间驱动的小批执行/背压作为硬配额内的平滑措施，覆盖每个处理阶段；不能降级成唯一保障。
- 平台/部署无法提供可验证硬限额时，任务保持等待配置或在创建前明确指出不可运行；**不静默切到软限额后宣称满足“不超过 10%”**。在支持其他平台前，必须实现并验证其进程组硬限制。

外部 SQL 的范围也必须诚实定义：嵌入式 SQLite 读取应在受控 worker 中执行；重型 SQL 不得绕回无配额的主服务。MySQL/PostgreSQL 等外部数据库查询消耗不自动受 worker 的 cgroup 限制，须用可证明的数据库侧预算/隔离导出实例，并设置小批扫描、索引与超时。缺少端到端约束时不得宣称该部署的“导出全部 CPU”已满足上限；需要限制相关模式或明确阻止进入严格模式。

CPU 上限只约束导出新增工作；整个 Komari 的写入、探测、正常图表及必要记账不被一并压到 10%，也不通过压低全局并发来替代导出隔离。

### 6.8 流式读取、检查点与文件发布

```text
创建持久任务及范围预约 -> 在 10% 总预算内规划固定 manifest
-> 有界顺序读取 -> 小批解码/转换 -> 直接写 CSV .part
-> 必要时有界外部合并 -> flush/fsync/校验/原子发布 -> ready
```

- 同一次正常执行只完整解压同一旧归档一次，不按多个时间块反复从头解压；恢复导致的必要重读单独统计，不能增加已完成量。
- 新归档采用可独立解码的有界帧及简单索引。旧格式继续顺序兼容读取，不在升级时全量重压，也不在读取时重写历史。
- 预编译序列匹配与元数据，避免逐点重新哈希标签、反复 JSON 序列化。异常大单条记录有明确大小上限和错误。
- 原始长表默认稳定的来源/接收顺序，并保留观测时间；不要无必要地承诺全局观测时间排序。如果用户选择时间排序，必须显示额外排序阶段与空间成本，并将整个外部排序纳入同一配额。
- 汇总与兼容宽表只保留有界组装状态；预先确定列，空列允许保留，取消整份 CSV 的二次列整理。
- 固定数据水位、段租约与短事务/keyset 分页保证热冷交接不漏不重；节流等待不占长事务或写锁。
- 检查点包含确认完成的来源帧/记录游标、输出已提交字节偏移/行数、格式版本和累计校验状态；恢复只认已提交偏移，先截断未提交尾部，不能直接 append 产生重复行。
- 旧单流 zstd 不能从任意压缩偏移恢复时，使用已封口分段输出或回到最近可解码边界重读，并保持去重；UI 显示恢复工作，不虚报零成本续传。
- 输出记录计数与哈希在流式写入时累计；取消、校验失败或原子发布失败都不进入 ready。
- 逻辑 I/O 在每个有界协作批次核算，包括命中页缓存的读取，不能用固定时间内免检查的快路累积数 MB 突发与分钟级预算欠账。首次处理前建立基线，步骤间结算欠账时保持控制监视器运行，暂停和取消可中断等待。此项是进程逻辑读写节流，不声称是内核设备 I/O 硬限额。
- 已完成文件按相同授权、范围、快照、模式和格式版本复用；下载不重新读取数据、做动态压缩或重新生成 CSV。

### 6.9 其他资源预算与前台优先级

以下为待实测的初始目标，不能只限制 CPU 后放任其他资源：

| 项目 | 初始目标与规则 |
| --- | --- |
| 数据缓冲 | 不超过 32 MiB，队列背压，不无限预读 |
| 导出 worker 总内存 | 目标不超过 128 MiB，含运行时/解码器/所有缓冲，按受控进程组统计 |
| 输出/临时磁盘 | 创建时有界评估、运行时持续保护；不足则明确暂停/失败，不挤爆主库磁盘 |
| I/O | 小批、可暂停；另设可配置读写速率预算，不把 CPU 低误当磁盘无影响 |
| 排队 | 有界、公平、同参数幂等、重复任务合并；不能一个账户占满全部长期任务 |
| 热区/归档 | 必要实时记账、近期汇总与归档安全推进优先；导出不得用租约无限阻止留存 |

前台延迟、记账/汇总积压、内存或磁盘压力升高时，导出可以降速或暂停到 0，不能因预计剩余时间变长而突破 10%。暂停原因与恢复条件在任务详情可见；等待期间不持有写锁。

### 6.10 接口与实现模块清单

任务创建返回 202/任务身份；状态接口使用版本化的结构化字段，至少包含：

- 身份及参数：owner/scope、mode、category、范围、aggregation/interval、format_version、snapshot/manifest 身份。
- 生命周期：status、phase、phase_started_at、created/started/ready/expires_at、pause/retry/cancel 信息。
- 真实进度：progress_kind、phase_completed/total/unit、completed_input_bytes、decoded_records、written_rows、output_bytes、confirmed_checkpoint。
- 观测：heartbeat/progress 时间、吞吐、ETA 区间及置信状态、实际 CPU 配额与占比、暂停/节流时间。
- 文件与覆盖：ready 后的大小/校验、数据缺口、单位/实际精度和下载身份；服务器绝对路径不下发。

新前端不再把旧单个 `progress:int` 当总工作量。兼容字段只能表达明确文档化的含义，不继续生成虚假的 1–99 总百分比。

具体改动落点：

| 模块 | 需要交付 |
| --- | --- |
| `web/api/admin/history_export.go` | 有界任务 API、移除时间跨度假进度/整文件二次整理、兼容旧格式 |
| `pkg/metric/telemetry_export.go` 与归档读取 | 固定 manifest、流式迭代、消费确认、无重复完整解压、可恢复游标 |
| 独立 export-worker/部署配置 | 所有导出计算的进程组配额、资源与控制状态、无权限时明确处理 |
| 持久任务模型/仓库 | 状态、检查点、幂等、租约、恢复、ready 后 TTL；版本化迁移 |
| Web `HistoryExportCard.tsx` 与任务列表 | 明确后台、三模式、阶段进度、等待原因、ETA、刷新/断线恢复 |
| 对应协议/API 类型与 i18n | 不混用 mode/category，覆盖正常状态与全部暂停/恢复文案 |

## 7. 升级、历史恢复与回退

1. 先固定版本与一致性数据库副本，不在生产数据库上直接试验。
2. 新增分段精度/覆盖元数据、走势分钟账本和有界尾部的 schema；保持旧日/周期/校准数据不变。
3. 分开判断“指标图表可恢复精度”和“流量走势可恢复精度”。普通指标原始点存在，不等于完整流量计数链和基线也存在。
4. 细汇总仍在时直接利用；原始流量事件/计数链及必要基线完整时，使用同一增量算法有预算地回填分钟账本，并对账日/周期总量。
5. 只剩小时流量时，不拆分造出分钟精度。临时展示明确标记的小时历史或部分覆盖；新分钟数据积累后自动恢复完整 24h/20m 走势，不能整面板 500。
6. 图表全局 `legacyResolution` 退出查询决策；来源精度落实到序列与时间范围。
7. 新汇总/分钟账本可影子生成与比较；验证前不删除旧小时账本，不将重建流量再加到既有日期/周期/校准中。
8. 单独说明版本切换、停机区间和工具参数。当前离线迁移不等于自动启动转换与维护页面已实现；本补强不以文档替代该功能。
9. 回退必须处理 schema 与存储代次，防止旧进程误消费新任务；检查点、归档格式版本与备份清单同步适配。

## 8. 实施顺序与逐步 CI/E2E

本轮优先处理当前流量故障，之后再推进其他存储补强。每步完成对应数据库单测、集成、相关组件 CI 和存储场景的真实 HTTPS/Web E2E，再开始依赖它的下一步；文档检查不能替代代码验收。登录和已安装 Agent 作为环境准备及真实数据来源，不重复验收未改动的 TOTP、终端授权、Agent 安装/升级等旧功能，也不因这些旧流程的脚本断言阻断数据库验收。完整工作流的失败结果仍如实记录，数据库结论必须对应其自身证据。

| 阶段 | 交付 | 主要验收 |
| --- | --- | --- |
| R0 | 固定可复现基准与失败用例 | 源码版本、数据库副本、逐分钟分布、错误传播、并发屏障；原实现确实失败 |
| R1 | 流量分钟/尾部、快照与模块隔离 | 24h/20m 正确数值；今天/日计费/校准独立；故障时各子面板正确降级 |
| R2 | 图表跨层计划、来源精度元数据 | 重叠不重复、缺层回退、热尾边界、移除全局小时限制 |
| R3 | 图表物理层、增量晋升、前端完整窗口 | 1h–90d 及更长档位的点数/精度；迟到/重试/回收安全；大序列成本 |
| R4 | 后台三模式导出、真实阶段进度、持久 worker 与 10% 总 CPU 上限 | 小时级大冷导出、阶段/ETA/暂停、CPU/RSS、重复解压、取消/恢复、授权与下载 |
| R5 | 迁移/备份/恢复/混合负载总验收 | 数据对账、旧库升级、故障恢复、各 SQL 驱动、前台不饥饿与持续资源曲线 |

### 8.1 流量回归矩阵（新增必测项）

| 场景 | 断言 |
| --- | --- |
| now 在 :05/:25/:45 及整点附近 | 24h/20m 都能返回真实结果，不能只测整小时 start |
| 10m/20m/30m 三种间隔 | 1m 桶合法合并，边界与总和正确 |
| 同小时三个 20m 桶有 100/200/300 的不同增量 | 精确得到 100/200/300，而非 600/0/0 或均分 |
| 读请求捕获时间后，再受控提交新事件 | 快照一致、不误报 partial、不读入固定历史终点后的数据 |
| 1m 与输出桶首尾恰好重合、相邻查询、纳秒边界 | 半开区间不重复、不漏点；旧闭区间接口显式适配 |
| 当前未闭合分钟、后台尚未追平 | 返回真实尾部/as-of/追赶状态，不把未知当 0 |
| 前台请求并发、取消、缓存命中/失效 | 读取不消费 outbox；共享读取与账户隔离正确 |
| 走势故障注入 | 日计费与已结算历史仍展示；只在对应子面板标错 |
| 当天读取故障注入 | 已结算日期仍展示，当天标记未知，不整月清空 |
| 校准、非午夜重置、UTC/既有业务时区、DST 周期 | 保留当前业务口径，周期总量与调整不因走势改变 |
| 重启/计数器重置、迟到、未来观测、稀疏/离线、重复事件 | 幂等、不倒退、不因插值产生额外流量 |
| 仅小时迁移历史 | 明确粗精度/覆盖状态，不伪造分钟、日计费可读 |
| 256 与超过 256 节点 | 有界批量且共享快照，不触发全看板 InvalidArgument |
| outbox 正好 128 与积压大于 128 | 前台不承担追账和写锁，报告水位与积压 |

### 8.3 CSV 与资源验收

本节验收第 6 节的新增 CSV 约束。以下用例全部待实施/执行，不以本次文档修改标记为通过。

#### 8.3.1 组件 CI 与正确性

| 用例 | 必须证明 |
| --- | --- |
| 三种模式使用同一已知观测集 | 汇总按桶/算法、raw 逐观测、30s 取样各自正确；模式与 category 不混用 |
| 来源仅剩 rollup、原始部分过期 | 原始导出不静默变为汇总；缺口与选择项正确 |
| 时间上前 80% 稀疏、后 20% 极密集 | 不再以时间跨度给出“整个任务 80%”；阶段/已处理量与实际工作一致 |
| 阶段开始、切换及 finalization 慢 | 不显示虚假的总百分比；fsync/发布前绝不 ready/100% |
| 底层读取器预读、输入重复命中、恢复重读 | 完成量只计一次已确认处理的来源单元，不因 file offset 跳大 |
| 单大旧 zstd 流、新独立帧、热冷混合 | 进度口径和可恢复点真实；未知分母时不定进度且持续报告行数/输出量 |
| CPU 配额等待、磁盘等待、压力暂停、重试 | 状态/原因/心跳/最后进展/ETA 各自正确，不能装成 running 卡住 |
| 任务幂等、队列满、公平性、全局并发 | 一次创建只对应一次计算；所有任务合计共享 CPU 上限 |
| 重启发生在检查点/flush/fsync/rename 各阶段 | 截断未提交尾部并正确恢复，或者明确失败；不丢任务、不重复行、不发布坏文件 |
| 文件 TTL 与排队/运行时间 | ready 后才开始 48h，长任务不被完成文件清理逻辑误杀 |
| 账户切换、节点权限撤销、下载身份 | 任务/状态/缓存/文件均遵守授权，不能跨账户复用 |
| 不支持硬配额、配额配置失败或运行中下降 | 严格模式阻止/暂停，不能静默无限速继续；重新计算有效 CPU |
| 异常大记录、损坏归档、磁盘不足、取消 | 小内存有界，错误可解释，租约释放，后续任务仍可运行 |

对结果核对观测身份、条数、值、单位、范围、确定性哈希与模式专属聚合值。SQLite/MySQL/PostgreSQL/MariaDB 使用实际驱动验证读取快照/分页/恢复；外部 SQL 的 CPU 约束须独立证明，不能拿 worker 限额替代。

#### 8.3.2 真实前端 E2E

- 提交看到“后台任务”与三模式说明，返回任务身份，不等待文件生成；范围/实际精度/原始缺失提示正确。
- 关闭页面、刷新、短断网、重新登录相同账户后仍能找回任务；断网不会取消任务，重试轮询可恢复且不每秒报错。
- 不同阶段、限额/压力暂停、取消中、重试、恢复、失败与完成都有可观察的独立展示；未知 ETA 不显示虚假倒计时。
- 正常生成几十分钟至小时级文件期间，前端保持可操作，任务列表不会阻塞表单；完成后显示真实大小、格式与到期时间。
- 原始观测、图表汇总与兼容采样的文件名/任务信息/内容匹配；下载操作不触发另一次数据库扫描或解压。
- 故意拖慢最终落盘/发布时显示真实阶段，不能出现“100% 但无法下载”，也不继续沿用“生成 80%”假装总体进度。

#### 8.3.3 CPU 与持续混合负载资格验证

- 使用事故数据库一致副本，并补充超过 30d、多个归档、显著密度差异和压缩率差异的数据；必须实际处理大量冷数据，不用仅 sleep 的任务冒充小时级导出。
- 1 CPU / 1 GiB 下，资格运行至少持续 2h，并继续到选定大型任务完成或明确终态。构造足够大的真实输入使主要阶段受到持续考验；另保留较短、确定性的 PR 回归，短回归不能替代 R4/R5 的完整资格运行。
- 同时进行实际 Agent 上报/记账、正常 Ping、指定图表窗口、必要归档/留存与导出。排队多个任务，证明上限属于任务组而非每个任务。
- 在 C_eff 为 0.5、1、2、4、8 的可配置环境验证 10% 比例与容器/宿主机区别；包括 cpuset、祖先 quota、运行中配额降低和不具备硬限制能力的部署。
- 保存真实 CPU 组配置、C_eff 推导、quota/period/burst、所有 worker/子进程 CPU 时间及 1s/10s/全程曲线。默认安全余量应使观察上限不超过全部有效算力 10%；不能只用长时间平均或主进程 RSS 隐藏短期满核/子进程开销。
- 在规划、热数据查询、解压、JSON、外部排序、写 CSV、恢复重读、校验/发布分别施加高 CPU 输入，证明所有阶段都在同一上限内；机器空闲也不自动借用额外 CPU。
- 采集受控进程组 RSS/缓冲峰值、读写/解压量及次数、SQL 扫描量、吞吐、阶段计数、停顿原因、节流时间、前台 p95/p99 与积压，验证没有因限速导致热区无限积压。
- 初始前台目标：正常 Ping/图表不因导出占满资源而被拒绝；同负载 p95 相对无导出基线劣化不超过 20%。性能不足时降速/暂停导出，不降低正常读取并发来掩盖问题。
- 正常同一旧归档完整解压次数应为 1；主动故障恢复的必要重读另列，不允许用重复解压推进百分比。
- 运行中主动取消目标 1s 内响应，验证取消完成前不会发布文件、租约与临时空间最终回收、下一任务可运行。
- 备份/恢复包含任务状态、有效检查点、分钟账本/尾部、覆盖水位与版本化归档目录；还原后不误判 ready、不将未完成文件提供下载。

CI/E2E 证据记录精确代码/协议/Web/部署配置版本、源数据 manifest、运行时长、硬配额环境、结果哈希与资源报告。没有实测硬限制或两小时级验证的项保持未完成。

- 这是 warm/未规定页缓存的有限资源实验，不能代替冷盘吞吐、多小时文件缓存积累、CSV 前台 p95 或部署环境的 24h soak。测试不会用 worker 的 `memory.current` 冒充解压进程 RSS。

#### 容量是实现成本，不是清理脚本问题

- schema 升至 6；旧 schema 1–5 原地兼容升级，旧版本程序拒绝打开新格式。开启数据库只做小型 DDL/版本处理，不遍历历史载荷。

#### CSV 普通暂停与崩溃恢复分开

- Queue 的 resume 只重新排队，由独占 worker 判断。只有同一个仍存活 worker、完全相同的 committed 结构与未改变的输出 inode/size/mtime/系统元数据，才可以继续自己已经计算并落盘的摘要状态。
- 信任证明仅存在内存、最多 8 个任务；完成、失败、取消或显式恢复路径释放证明。不向队列持久化“已校验”开关。进程重启、手动 retry、队列还原、文件被替换/截短/同长度改写等仍从 byte 0 校验。
- 校验途中再次暂停不能授予“已校验”证明；保留现有 regression。只丢弃未提交尾部，按 durable checkpoint 继续，不跳过已提交前缀校验、不放宽哈希要求。
- 有限复现使用 26,214,400 字节前缀和 131,072B/s 配额：同 worker 普通恢复不再重新读取 26MB；新 worker 明确进入 byte-0 recovering，可立即取消。独立 systemd 进程 CPUQuota=4%、MemoryMax=128MiB、swap=0，同 worker约 17.7ms 完成该有限发布步骤。该实验使用合成输出及 fixture 资源证明钩子，不等于真实两小时 E2E 验收。
- 资格脚本的 30 秒普通恢复门限、CPU 10%、前台 p95 1.2 倍及内存门限均不变；暂停/恢复每个 GET 的真实状态、phase、wait_reason、verification 单独落盘，资源采样不再沿用外层旧 job。
