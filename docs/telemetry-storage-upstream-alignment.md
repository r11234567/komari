## 1. 采用的方向

主库已经承担降采样，采用 Komari 当前的规范化统计行、字典和按需读取思路；全量原始数据持久化/归档与任务调度作为独立职责接入。缩小自研存储范围，不继续把每个历史统计桶永久绑定到归档 owner、导入窗口和接收收据。

**以 Komari 的规范化统计模型为主要参考，不重新接回 Lite 的 V4/V9 块存储。** 这里的“接上全量数据和调度”还包括持久输入的适配：上游精确点仅驻留内存，不能作为已经确认接收后的唯一来源；原始点、流量交接与统计水位仍须落盘。需要保留的是这条可靠输入契约，不是另一套永久在线的统计引擎。

统一数据流为：

```text
上报 -> 一次可靠热表提交（幂等身份、待记账事件）-> 接收确认
              |
              +-> 有界增量统计 -> 小型在线统计 SQL -> 图表
              +-> 独立业务账本 -> 累计/周期/校准/计费
              +-> 流式不可变 JSONL-zstd -> 后台导出

调度器按各自持久进度推进；归档、统计、必要记账交接均完成后才回收热明细。
```

归档任务不负责生成图表；统计 SQL 不负责保存全部明细；普通图表不触发冷文件解压。保持原方案的数据安全不变量，减少实现它们所用的重复表和逐桶状态。

## 3. 主库具体收敛

### 3.1 字典与桶身份

一个逻辑桶以整数序列、分辨率和桶起点定位。标签是否参与身份沿用已对外承诺的维度，不因去重把不同曲线混在一起；字典中保留完整 canonical 身份，不截断 hash 代替唯一性。

- 分辨率使用短整数引用，避免每行重复存纳秒级 duration。
- 桶边界只采用实际分辨率所需的时间精度；原始观测和 first/last 的纳秒及稳定次序另保留，避免直接截成毫秒造成同时间观测换序。
- SQLite 对比一棵 `WITHOUT ROWID` 主树与上游普通行/索引组合，按节点查询、看板批量读取和到期回收的 EXPLAIN、体积与耗时选最小必要索引。不能只比较裸表而漏算唯一索引和二级索引。
- 永久桶主键移除 `segment_id`；归档目录只对应真实文件。已完成迁移窗口、旧 owner 和收据不再按历史桶永久保留。

### 3.2 统计载荷

采用上游的按需读取原则：均值图只读 count/sum，极值图只读极值，方差图只读可合并矩；只有分位图/统计卡片读取分布。比较两种实际布局，再选定生产格式：常用标量列加独立压缩 digest，或标量列加紧凑二进制扩展。逐行整体 BLOB 只能作为比较项，不能让均值查询继续被迫解压无关分布。

必须保留本项目现有语义：

1. 有效时延数、总探测次数、失败次数分开；全丢包桶仍有真实人口。
2. 继续保留数值稳定的 M2 合并状态，避免从 `sum_sq - sum*sum/n` 恢复方差时发生大基数、小波动的抵消误差。
3. first/last 的原时间和稳定顺序保留，不直接照搬毫秒时间平局行为。
4. 恒定有效值分布可由值和有效数量精确描述；全失败/空有效人口使用独立编码。非恒定桶，包括两个不同样本的桶，仍保存分布。
5. 常量摘要省略需要有格式版本/标志，读取与晋升共同恢复其权重；不能把任意缺失摘要解释成常量。
6. 上游应用默认 t-digest compression=30 与本项目现有精度不相同。格式压缩保持已有质心；不将降低 compression 或丢弃 P95/P99 算作无损节省。
7. zstd 仅在实际节省字节时使用，直接保存 BLOB；旧 JSON/Base64 只保留有界读取兼容。

### 3.3 可靠输入与晋升

上游的内存分钟/粗桶累加器可以作为缓存参考，持久输入仍由我们的热表提供。统计结果、消费水位和必要的脏范围在同一事务提交；重启从水位恢复，不能因内存分钟丢失而永久少计，也不能重放一次就重复累加。

迟到上报沿用原接收时间窗，修正只影响对应桶与祖先范围。父级覆盖相同输入水位后才能删除子级；迁移只有旧粗桶而没有完整细来源时仍保留真实粗精度，不拆桶。闭合父桶写完整统计，避免每个上报都扫描完整历史或读改写一整块。

长期幂等与流量交接以有限生命周期水位/收据实现；删除前置条件继续存在，但不借此把接收历史和每个旧迁移窗口永久塞进桶键。

## 4. 全量归档和调度怎样接上

### 全量数据引擎

- 一次可靠热表提交同时供统计、流量和归档消费，不为三个消费者保存三份明细。
- 正常热明细按一天预算回收；归档/统计/必要记账未完成时保留数据并报告积压，不能到点硬删。
- 复用现有不可变 JSONL-zstd、校验、原子发布、恢复和删除前置检查；替换其与逐桶永久 owner 的耦合。
- 段目录、帧索引记录真实观测时间及适用序列范围。CSV 按观测范围选帧，降低导入大 owner 导致的选择放大；兼容旧归档时仍有字节/内存预算。
- manifest 以实际编码字节及驻留内存为预算，保留逐帧 checkpoint；不再用一个与实际工作量脱节的固定帧数代替资源控制。
- CSV 三模式、真实阶段进度、后台任务与所有导出合计 10% 有效 CPU 上限继续执行。

### 调度引擎

- 统计推进、归档发布、热表交接删除、桶留存、目录回收、CSV 分开持久化进度；清理不夹在前台读取里。
- 复用维护互斥门与短事务思想，各工作片拥有行数、时间和资源预算；有进展续排，失败退避，空闲降低频率。
- 保留 `10s/1h -> 1m/1d -> 5m/7d -> 15m/14d -> 1h/指标总留存`。已有一天窗口仍可组合为 12h/2m、1d/4m；长期按 15d 递增。
- 上游五分钟 flush/一小时清理是其具体实现，不直接作为近期 10s 图和大积压场景的固定配置。最近未封口范围继续通过有界持久热尾查询满足新鲜度。
- 上游粗桶封口宽限为十分钟，超过宽限的分钟替换不再反馈到已封存父桶。这不能代替本项目已承诺的迟到窗口；持久输入适配需要记录受影响范围，并从仍可用的完整子来源重建父统计。分位摘要不可直接做减法；无法精确重建时必须暴露真实覆盖情况，不静默丢掉迟到人口。
- 正常无积压时不每半分钟全库扫，不定期重压完整历史，不让维护任务彼此叠加。

## 5. 结构删除与接入顺序

1. **先验证主库。** 固定留存、活跃序列、标签和相同统计人口，比较当前紧凑 BLOB 与参考规范化行；逐条验证标量、分布、丢包、时间/稳定身份，并量完整表与索引。源码对照不是容量达标证据。
2. **接入规范化统计。** 由现有可靠热表驱动，统计/水位原子提交；图表读按聚合投影，保留真实覆盖范围和跨层组合。旧单一分辨率选择器不进入新查询路径。
3. **解耦并删除历史状态。** 归档文件 owner 与桶主键分离；完成交接后回收旧迁移窗口、旧 membership、过期收据和旧维护索引。删除时有恢复/幂等证明，不保留两套永久在线统计引擎。
4. **接回归档和调度。** 复用已有验证有效的文件交接、账本和后台任务，补齐 CSV 选择/manifest 预算；验证磁盘满、取消、重启、迟到、删除及长时间离线恢复。
5. **最终迁移切换。** 旧库自动识别并在受限启动阶段转换；完成后安装并重开，新旧数据、账本和图表对账，保留独立回退材料。旧块引擎只留下迁移读取入口，退出新运行路径。

每一步只验证数据库相关功能：生产和兼容构建、race/vet、必要 SQL 驱动、图表/记账/归档/恢复 E2E；真实事故验证在本地进行。生产布局完成后重新量总容量与资源，再决定能否发版；不沿用前一版 CI 证明未来改动，也不引入 TOTP/Agent 升级等无关步骤。

## 6. 本轮比较已经证实什么

固定 Komari 参考版本的 `pkg/metric` 整包 race 与 vet 已通过。它验证的是参考包本身，不覆盖本项目的热表、跨库账本、自动迁移或归档导出。

本地布局实验使用相同来源、留存、统计人口、分位质心、丢包、稳定顺序、一天热明细及归档目录；不改动原事故库，不安装试验布局，不上传真实材料。逐行重读验证所有标量、首末身份和非恒定分布字节；恒定分布验证权重及分位恢复，完整性检查通过。容量和日志仅保留本地。

实验排除了两个容易误判的结论：

1. **普通统计列不等于数据库必然足够小。** 独立摘要、常量分布省略和紧凑排序信息确有收益，但在相同留存下仍未达到约定的容量目标。不能用上游较低的 t-digest compression 或更粗的查询层级制造容量达标。
2. **单棵主树的体积不等于可上线的总库体积。** 按上游普通行表、唯一索引和两条查询索引的形状补齐后，文件显著增大；只留 series-first 主树时，单序列查询能定位，广域按时间查询却出现全表扫描和临时排序。最终布局必须同时核对完整索引、真实选择率、回收扫描和恢复元数据。当前暖缓存 SQL 投影耗时不能当成 HTTP 图表延迟或并发验收。

因此，方向已确定为规范化统计主库；**最终物理布局尚未定型，也未将布局试验宣称为代码已完成接入**。优先减少重复键、无效常量分布和永久历史归属，选择能服务实际查询的最少索引；不为追求单一体积数字删除统计含义或重新引入整块反复重写。

## 7. 接入边界与逐步验收

| 边界 | 明确职责 | 完成条件 |
| --- | --- | --- |
| 接收 → 持久热表 | 原始值、完整身份、接收序号、幂等及待记账事件一次提交；缓存可丢 | 提交前失败不 ACK，提交后重启/重复请求不丢失、不重复计费；改变重试内容拒绝 |
| 热表 → 规范化统计 | 有界读取输入，事务内更新统计、水位及需修正范围；封口后不再反复扫描全部历史 | 同时刻稳定首末值、全失败 Ping、数值稳定方差、分位合并、迟到修正、取消和重放对账 |
| 统计 → 图表 | 先解析序列字典，按聚合读列；按覆盖组合层级，最近边缘读同快照热尾 | 既定窗口及长期每 15d 递增；边界、缺口、混合层、标签身份、无冷读及查询分配预算全部通过 |
| 热表 → 业务账本 | 独立消费接收序号；整数 Bytes、业务日期、周期及校准保持原语义 | 跨库中断恢复、重复投递、时区边界、正负校准一致；走势图出错不影响计费 |
| 热表 → 原始归档 | 流式不可变 JSONL-zstd，实际时间/序列的段和帧索引；发布校验后推进归档水位 | 中断/磁盘满/校验失败均不放行删除；发布成功但进度未提交可恢复 |
| 调度 → 回收 | 分开推进统计、归档、热删除、桶留存和元数据回收；有限生命周期收据维持可接受重试的幂等 | 必要消费者全部完成才删；无工作退让、有积压有界续排、失败退避、不重叠；不永久保留迁移窗口 |
| 归档/统计 → CSV | 三模式后台任务；按实际选择的帧与字节预算生成可续跑 manifest | 修复帧选择放大与固定帧数上限，不单纯加大 cap；取消、恢复、进度及全部导出合计 10% CPU 验证 |
| 旧库 → 新布局 | 受限启动、断点迁移、独立回退材料、校验后切换 | 实际服务重启、新旧人口/值/业务账本对账；不恢复旧块运行路径；迁移副本及恢复材料计入磁盘峰值 |

实施按第 5 节推进，先完成主库的结构、查询和恢复契约，再接回独立归档与调度。每一阶段同时交付实现与对应数据库验证，最后以生产布局完整重迁移后的在线 SQL、归档、WAL/SHM、恢复元数据及资源测量验收；约 50 MB 仍是目标，不是此次参考源码后已经达到的结果。
